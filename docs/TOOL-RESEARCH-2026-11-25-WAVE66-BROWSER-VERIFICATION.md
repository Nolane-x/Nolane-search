# Wave 66 — live browser playback validation

Date: 2026-11-25  
Branch: `feat/wave-66-hls-dash-browser-playback`  
Purpose: close the remaining release gap between unit tests and real third-party HLS/DASH playback.

## Why a separate browser gate is needed

The existing Vitest suite verifies player wiring, request filters, CSP, manifest resolution, cleanup and JavaScript syntax. It cannot prove that a public origin is online at test time, returns the child playlists/segments with usable CORS headers, or serves codecs that the selected browser can decode.

This follow-up adds two complementary checks:

1. **Playback Lab inside Media Portal** — a user can choose a curated public stream, let the real URL resolver render a player card, then explicitly press Play and test the controls.
2. **GitHub Actions browser gate** — Playwright launches a real headless Chromium, serves the actual `mediaAppResponse()` HTML generated by `src/media-ui.ts`, and loads HLS.js 1.7.4 / dash.js 5.3.0 from their pinned CDN URLs. The test harness stubs only owner-session and URL-resolver API responses. Manifests, child playlists, segments, audio and subtitle resources are fetched directly by Chromium from their actual third-party origins. No media payload is mocked or proxied.

These are public test vectors, not uptime-monitored production sources. Their publishers can change them, geoblock them or remove them. The test therefore records source URL (without query), HTTP status, content type, CORS response header, failed browser requests, player errors and observed controls. A failed sample must be classified as an upstream/source failure or a player regression before changing production code.

## What the browser gate asserts

For each sample:

- The real Media Portal page loads and completes its owner-session boot path (only the test harness response for `/api/auth/me` is synthetic).
- The real UI submits the URL to its resolver route and creates an HLS or DASH card.
- The real lazy loader requests the pinned player library; the manifest and media resources are requested by Chromium directly from the public origin.
- Playback advances beyond two seconds. A valid response to the master manifest alone is not enough.
- HLS Mux exposes at least two video variants plus Auto; the test asks the UI for a manual quality.
- Shaka HLS exposes at least two audio options and the test selects an alternate.
- JW HLS exposes at least one subtitle plus Off and the test selects a subtitle.
- Shaka DASH Angel One exposes multiple video representations, multiple audio tracks and at least one text track; the test changes each where exposed.
- Shaka DASH Sintel exposes multiple representations and a text track.
- Playback rate can be changed to 1.25×.
- HTTPS request failures, CORS errors, player errors and console failures relevant to media playback are recorded.

The browser test is intentionally strict for expected capabilities: an absent expected track is a failed test result, not a silent pass. If an external sample is unavailable, replace it with another openly accessible sample that tests the same feature and record why the original was retired.

- Timeout override: `MEDIA_E2E_TIMEOUT_MS=55000`
- Output: `artifacts/media-playback-report.json` plus a GitHub Actions step summary and uploaded artifact.

The browser test deliberately uses the app's actual generated HTML. It does not start the production Worker or pretend the test harness's synthetic owner session is a test of production authentication. It focuses only on the missing browser/media interoperability evidence. Authentication, URL resolver, request-filter and security boundaries remain covered by the existing Worker/Vitest tests.

## First live-browser findings (2026-11-25)

The initial real-browser matrix produced a useful split result rather than a pass:

- The HLS Mux ABR, Shaka Angel One HLS and HLS WebVTT cases all reached at least two seconds of playback in Chromium. The browser observed multiple quality options for Mux and Shaka; Shaka exposed six audio entries plus text tracks; the WebVTT playlist exposed a subtitle track plus Off. CORS evidence showed successful public manifest/child-playlist responses with `Access-Control-Allow-Origin: *`.
- That run also exposed a real UI defect: the playback-rate select had been created but was not appended to its label. The player now appends the caption and select, and the browser test verifies 1.25×.
- HLS.js can emit WebVTT track content using a `data:,WEBVTT` URL. Chromium reported the previous `media-src` policy blocking this in-band data track, so `data:` was added only to `media-src` (not `script-src`).
- Both DASH samples initially failed before any MPD request. The browser diagnostic recorded `event type cannot be null or undefined`. Source inspection of dash.js 5.3.0 showed that license/protection events are exposed through `dashjs.Protection.events`, not `dashjs.MediaPlayer.events`. The DRM stop listener now uses `dashjs.Protection.events.LICENSE_REQUEST_SENDING`. This keeps the intended no-DRM policy while allowing a non-DRM player to initialize.
- The corrected implementation is running again in the release gate. Do not call DASH verified until the new run records the MPD request, media advancement and expected quality/audio/subtitle controls.

## Native-HLS routing correction

The earlier native fallback used `video.canPlayType('application/vnd.apple.mpegurl')` as the only signal. The CI Chromium build returned `maybe` even though it did not behave as the intended native-HLS path; all three HLS fixtures consequently skipped HLS.js. The player now:
- prefers native HLS only when the browser identifies as Apple WebKit and reports native HLS support;
- keeps HLS.js as the normal path for Chromium/Firefox and other browsers;
- uses native HLS as a fallback if HLS.js is unsupported or its CDN cannot be loaded on the detected Apple WebKit route;
- keeps the video element anonymous and no-referrer on the native path.

This fixes the CDN dependency for Safari/WebKit without sending Chromium into a false-positive native route. The smoke check validates routing only; manual Safari/iOS decode validation is still a separate gate.

## Boundaries that remain

- This gate is Chromium/MSE coverage. It does not simulate Safari's native HLS stack. Native HLS remains a separate manual test on a real iPhone/iPad or Safari/macOS client.
- Codec availability varies by OS, browser build and hardware acceleration. A passing Chromium run is not a universal browser/device compatibility claim.
- This gate does not test DRM playback and is expected to keep protected test assets out of the supported matrix. The product must continue to stop on DASH license requests.
- A successful run is time-bound evidence for the five tested origins. It is not a guarantee of future upstream uptime.
- The browser gate distinguishes `net::ERR_ABORTED` request cancellations from actual network failures. When the player manually changes representation, an in-flight request for a now-unselected high-bitrate segment can be aborted normally; the gate still requires playback to advance, the selected quality handler to run, and it continues to fail on CORS, HTTP, DNS, manifest or decoder errors.
- The browser test does not deploy or merge anything. Production release remains blocked until the current browser gate passes and the Safari/native-HLS manual check is recorded.

## Real Safari native-HLS decode gate

The Chromium matrix does not prove Safari native decoding. A separate macOS GitHub Actions workflow now runs the real Apple Safari browser through the operating-system `safaridriver` WebDriver, using the exact Media Portal HTML and a public HLS source. It asserts Safari's native-HLS capability, that the UI selects its native path without loading HLS.js, that `video.play()` succeeds, and that the video advances beyond one second with `readyState >= 2` and no media error. It uploads a machine-readable report and screenshot.

- Workflow: `.github/workflows/media-safari-native-hls.yml`
- Script: `scripts/media-safari-native-hls-e2e.mjs`
- Runner: `macos-15-intel` (Apple Safari + built-in `safaridriver`)
- Source: `https://test-streams.mux.dev/x36xhzz/x36xhzz.m3u8`

The workflow uses Apple's documented Safari WebDriver enablement command (`safaridriver --enable`) and W3C WebDriver session. A successful run is direct Safari/macOS evidence for that Safari version and source at that time; it is not iOS Safari certification, and it does not guarantee all HLS sources/codecs. The Chromium matrix remains responsible for HLS.js and DASH behavior.
